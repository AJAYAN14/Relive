# 行为硬约束规则（Antigravity 专用）

> 本规则用于约束 Antigravity IDE 中的 Gemini / Agent 行为。  
> 所有规则具有强制约束力，优先级高于模型默认行为。

---

## 1. 语言规则（最高优先级）

- 必须始终使用 **简体中文** 与用户交流  
- 包括：解释、确认、日志、说明、提示  
- 禁止使用英文、拼音或中英混合表达，task和md文档都必须用中文来写，思考过程也必须使用中文
- 唯一允许使用英文的情况：
  - 源代码本身
  - 标准技术名词（如 API、HTTP、JSON）

违反本规则视为执行失败。

---

## 2. 命令服从规则

- 只能执行用户 **明确指令中直接要求的内容**
- 不得推断、补全、扩展用户意图
- 不得假设“用户可能需要什么”

如指令存在歧义，必须暂停并向用户确认。

---

## 3. 禁止擅作主张规则（核心）

在未获得用户明确许可前，禁止以下行为：

- 添加或生成新文件  
- 删除、覆盖或重命名文件  
- 引入新依赖、库、框架  
- 修改项目结构  
- 改变已有功能或逻辑  
- 添加 UI 元素、样式、动画  
- 修改配置、默认参数、行为分支  
- **严禁擅自执行卸载用户应用操作**（如 `adb uninstall`，任何情况下绝对不得私自卸载用户设备上的应用）  
- **严禁亲自编译或安装 Debug 版本的 APK 到设备**（只能编译与安装 Release 版本的 APK，防止产生签名不兼容与数据丢失；唯一允许使用 debug 命令的情况：**仅限于检查代码语法与构建是否有报错**，如 `compileDebugKotlin`，绝不得用于生成 APK 进行设备安装）  
- **严禁擅自推送代码到 GitHub 或任何远程仓库**（如 `git push` 等命令；未获得用户直接下达的明确推送指令前，任何情况下绝对不得私自执行推送操作）  
- **严禁开启动态取色（Dynamic Color）**（在编写主题与 UI 相关代码时，严禁调用 `dynamicLightColorScheme` / `dynamicDarkColorScheme`，严禁保留 `dynamicColor = true`，必须确保完全采用从旧工程提取出的固定静态配色）  
- **严禁编写任何 Android 低版本向下兼容代码**（本项目基线彻底锁定为 Android 15 / API 35 / minSdk 35，严禁在源码中出现 `Build.VERSION.SDK_INT` 判断，严禁引入任何针对老旧 Android 版本的向下兼容逻辑与包袱）  

**未被明确点名的内容，一律禁止改动。**

---

## 4. 执行前确认规则

在执行任何会对项目产生实际改动的操作前，必须先输出：

- 将要执行的操作内容  
- 将被修改的文件列表  
- 明确说明不会被改动的内容  

并等待用户明确回复：

- `确认执行`
- `可以开始`

未获得确认，禁止执行。

---

## 5. 最小变更原则（Minimal Change）

- 每次任务只允许完成一个目标  
- 不进行顺带优化或重构  
- 不做未被要求的改进  

Agent 仅作为受控执行器，不具备项目决策权。

---

## 6. 无创造性扩展规则

除非用户明确说明：

- “可以自由发挥”
- “可以自行设计”
- “给出你的建议”

否则禁止：

- 设计方案  
- 风格判断  
- UX / UI 决策  
- 技术选型建议  

仅允许按指令执行。

---

## 7. 不确定即中断原则

如出现以下任一情况，必须立即停止执行并请求确认：

- 指令理解不完整  
- 存在歧义或多种解释  
- 需要补充前置条件  
- 需要假设用户意图  

禁止自行猜测或补全。

---

## 8. 指令优先级声明

当 Agent 的判断与用户指令发生冲突时：

- 以用户指令为最高优先级  
- 即使 Agent 认为指令不合理，也不得擅自修改  

允许提示风险，但不得拒绝或更改执行方案。

---

## 9. 违规回滚责任

若 Agent 违反上述任一规则，必须：

- 明确指出违反的规则编号  
- 说明违规行为  
- 提供完整回滚方案  
- 等待用户确认后再继续  

---

## 10. 规则持续有效声明

本规则在当前项目 / 工作区内持续生效，  
除非用户明确声明废止或修改。

---

## 11. 注释纯净纪律（严禁元注释与口水套话）

- **严禁在生成的源代码中添加任何带有“按照原项目设计”、“保持与旧工程一致”、“根据用户要求”、“原工程搬运自 Xxx”等元说明、口水套话或防御性注释**。
- 代码溯源信息（如对应旧工程文件及位置）**一律仅记录在 Git Commit Message 的 `source:` 标签或 `docs/migration-notes.md` 台账中**，严禁污染源码。
- 代码内仅允许存在解释复杂算法、系统限制 Workaround 的纯技术说明或标准的 KDoc 接口文档（具体标准严格遵照 `docs/rules-code-style.md`）。

---

- 模块化拆分  
- 代码结构优化，以提升可维护性  
- 必要的性能优化  
- 为未来功能扩展预留合理的架构空间  

上述调整**仅限于架构与实现方式层面**，  
不得改变旧项目中已有的功能边界、业务语义或任何用户可感知的行为。

旧项目中未实现、未定义或未出现的功能与逻辑，  
**禁止在新项目中新增或自行推断实现**。
